# ТЕХНИЧЕСКОЕ ЗАДАНИЕ
## Разработка веб-приложения для анализа данных криптовалютных рынков

### 1. Основание для разработки

Разработка обусловлена необходимостью создать архитектурную и функциональную основу для сервиса, который обеспечивает:

- сбор рыночных данных с криптовалютных бирж;
- приведение данных разных бирж к единому формату;
- сохранение исторических рыночных данных;
- расчёт аналитических показателей;
- отображение результатов анализа в веб-интерфейсе;
- предоставление программного доступа к данным через API.

### 2. Назначение разработки

Создание веб-приложения LiquiDyne для анализа данных криптовалютных рынков и оценки рыночного риска по выбранным торговым парам.

Система предназначена для пользователей, которым необходимо отслеживать состояние рынка, смотреть динамику цены, объёма, открытого интереса, ликвидаций и общего показателя риска.

### 3. Цели разработки

Целями разработки являются:

- проектирование масштабируемой системы сбора и обработки рыночных данных;
- реализация серверной части с разделением на независимые сервисы;
- создание веб-интерфейса для просмотра аналитики;
- реализация авторизации пользователей и управления API-ключами;
- организация хранения исторических данных;
- подготовка проекта к развёртыванию в контейнерной среде;
- обеспечение проверяемости системы с помощью автоматических тестов.

### 4. Требования к функциональным характеристикам

Система должна обеспечивать следующие функции:

- регистрация, вход и подтверждение почты пользователя;
- выдача и обновление JWT-токенов;
- создание и отзыв пользовательских API-ключей;
- получение списка поддерживаемых бирж и торговых пар;
- сбор рыночных данных с HyperLiquid и Binance;
- обработка сделок, ликвидаций, открытого интереса и свечных данных;
- сохранение рыночных событий и агрегированных данных в PostgreSQL;
- расчёт аналитических показателей:
  - всплески ликвидаций;
  - изменение открытого интереса;
  - соотношение объёма торгов и ликвидаций;
  - общий показатель риска от 0 до 100;
- отображение основной панели с рыночными метриками;
- отображение временной шкалы риска;
- поддержка режима обновления данных через поток событий;
- ведение списка наблюдаемых торговых пар;
- предоставление REST API для веб-интерфейса и внешних клиентов;
- предоставление OpenAPI-документации.

### 5. Требования к надёжности

Система должна обеспечивать:

- сохранение рыночных данных и результатов аналитики в PostgreSQL;
- идемпотентную запись рыночных событий, чтобы повторная обработка не создавала дубликаты;
- повторное подключение к источникам данных при временных сетевых сбоях;
- пакетную запись данных для уменьшения нагрузки на базу данных;
- проверку работоспособности сервисов через health endpoints;
- резервное копирование PostgreSQL;
- восстановление базы данных из резервной копии;
- ограничение размера входящих запросов;
- ограничение частоты запросов для публичных, авторизационных и пользовательских маршрутов.

### 6. Условия эксплуатации

Система рассчитана на эксплуатацию в веб-среде:

- доступ к пользовательскому интерфейсу через современные браузеры;
- доступ к серверному API по HTTPS;
- работа серверной части на Linux-сервере;
- запуск сервисов в Docker-контейнерах;
- публичный доступ только через nginx;
- внутренняя связь сервисов в закрытой Docker-сети.

### 7. Требования к составу и параметрам технических средств

Для работы серверной части требуется:

- сервер с ОС Linux;
- Docker Engine и Docker Compose;
- PostgreSQL 17+;
- Kafka 4+;
- nginx;
- Go 1.26+ для сборки серверной части;
- Node.js для сборки клиентской части.

Рекомендуемые параметры сервера для учебной и демонстрационной эксплуатации:

- процессор: от 2 ядер;
- оперативная память: от 2 ГБ;
- дисковое пространство: от 20 ГБ;
- сетевое подключение: от 100 Мбит/с.

### 8. Требования к информационной и программной совместимости

Система должна быть совместима со следующими технологиями и форматами:

- HTML5, CSS3 и JavaScript в клиентской части;
- REST/JSON для внешнего API;
- Protocol Buffers и gRPC для внутреннего взаимодействия сервисов;
- PostgreSQL для постоянного хранения данных;
- Kafka для передачи рыночных событий между сервисами;
- OpenAPI для описания внешнего API;
- Docker Compose для локального и серверного запуска.

### 9. Стадии и этапы разработки

Разработка выполняется по следующим этапам:

1. Проектирование архитектуры серверной части.
2. Реализация доменных моделей и базовых проверок.
3. Создание схемы базы данных и миграций.
4. Реализация работы с Kafka.
5. Реализация авторизации и API-ключей.
6. Создание gRPC-контрактов между сервисами.
7. Реализация внешнего REST API.
8. Реализация адаптеров бирж HyperLiquid и Binance.
9. Реализация сбора и сохранения рыночных данных.
10. Реализация аналитических расчётов.
11. Реализация веб-интерфейса.
12. Реализация контейнеризации и развёртывания.
13. Настройка автоматических проверок и доставки обновлений.
14. Проведение тестирования и устранение ошибок.

### 10. Порядок контроля и приёмки

Контроль качества выполняется с помощью:

- модульных тестов доменной логики и расчётов;
- контрактных тестов адаптеров бирж и внутренних интерфейсов;
- интеграционных тестов PostgreSQL и Kafka;
- тестов внешнего API;
- end-to-end тестов полного пути данных;
- проверки сборки серверной и клиентской части;
- проверки конфигурации Docker Compose;
- проверки соответствия реализованных функций требованиям технического задания.

# ОПИСАНИЕ ПРОГРАММЫ
## LiquiDyne — веб-приложение для анализа данных криптовалютных рынков

## 1. Общие сведения

### 1.1. Обозначение и наименование программы

- **Обозначение:** LiquiDyne
- **Наименование:** веб-приложение для анализа данных криптовалютных рынков
- **Краткое наименование:** LiquiDyne

### 1.2. Программное обеспечение, необходимое для функционирования

Для работы программы используются:

- ОС Linux;
- Docker Engine;
- Docker Compose;
- nginx;
- PostgreSQL 17+;
- Kafka 4+;
- Go 1.26+;
- Node.js;
- веб-браузер с поддержкой HTML5, CSS3 и JavaScript.

### 1.3. Языки программирования и технологии

- Go — серверная часть и бизнес-логика;
- TypeScript — клиентская часть;
- React — пользовательский интерфейс;
- SQL — работа с базой данных;
- HTML5 и CSS3 — разметка и оформление интерфейса;
- Protocol Buffers — описание внутренних контрактов;
- REST/JSON — внешний API;
- gRPC — внутреннее взаимодействие сервисов.

## 2. Функциональное назначение

### 2.1. Класс решаемых задач

Программа предназначена для решения задач анализа криптовалютных рынков:

- автоматический сбор рыночных данных;
- хранение истории по торговым парам;
- расчёт показателей рыночного риска;
- построение временной шкалы риска;
- отображение аналитики в веб-интерфейсе;
- предоставление данных внешним клиентам через API.

### 2.2. Назначение программы

LiquiDyne создаёт единый слой между криптовалютными биржами и пользователем. Система получает данные с бирж, нормализует их, сохраняет в базе данных, рассчитывает аналитические показатели и показывает результат в виде панелей, таблиц и графиков.

Программа может использоваться как учебный прототип аналитической платформы для отслеживания состояния криптовалютного рынка.

### 2.3. Функциональные ограничения

- Система не принимает торговых решений автоматически.
- Результаты аналитики носят информационный характер.
- Качество показателей зависит от полноты и доступности данных бирж.
- Для получения актуальных данных требуется сетевой доступ к внешним API бирж.
- В текущей версии поддерживаются HyperLiquid и Binance.
- Сложные модели машинного обучения не входят в область текущей версии.

## 3. Описание логической структуры

### 3.1. Алгоритм работы программы

```text
Начало
├── Пользователь открывает веб-интерфейс
├── Пользователь проходит регистрацию или вход
├── Система выдаёт токены доступа
├── Пользователь выбирает биржу и торговую пару
├── Сервер получает список доступных торговых пар
├── Сервис сбора данных подключается к бирже
├── Адаптер биржи приводит события к единому формату
├── Рыночные события отправляются в Kafka
├── Сервис хранения читает события из Kafka
├── Данные сохраняются в PostgreSQL
├── Сервис аналитики рассчитывает показатели риска
├── API отдаёт данные веб-интерфейсу
├── Интерфейс показывает панель, таблицы и графики
└── Конец
```

### 3.2. Используемые методы

В программе используются следующие методы и подходы:

- клиент-серверная архитектура;
- микросервисная организация серверной части;
- событийная обработка данных через Kafka;
- хранение истории в PostgreSQL;
- адаптеры для подключения разных бирж;
- REST API для взаимодействия с клиентским приложением;
- gRPC для внутренней связи сервисов;
- контейнеризация через Docker и Docker Compose;
- автоматическое тестирование разных уровней;
- документирование API через OpenAPI.

### 3.3. Структура программы

#### 3.3.1. Основные серверные модули

1. **api-gateway**
   - Принимает внешние HTTP-запросы.
   - Проверяет авторизацию.
   - Передаёт запросы внутренним сервисам через gRPC.
   - Отдаёт OpenAPI-документацию.

2. **auth-service**
   - Выполняет регистрацию и вход пользователей.
   - Подтверждает почту.
   - Выпускает JWT и refresh-токены.
   - Управляет пользовательскими API-ключами.

3. **symbol-service**
   - Синхронизирует список торговых пар.
   - Хранит сведения о биржах и символах.
   - Предоставляет список активных рынков другим частям системы.

4. **market-ingestor**
   - Подключается к биржам.
   - Получает сделки, ликвидации, открытый интерес и свечные данные.
   - Приводит данные к внутреннему формату.
   - Публикует события в Kafka.

5. **market-storage**
   - Читает рыночные события из Kafka.
   - Сохраняет данные в PostgreSQL.
   - Выполняет пакетную запись.
   - Обеспечивает защиту от дублирования событий.

6. **analytics-service**
   - Рассчитывает аналитические показатели.
   - Формирует оценку риска.
   - Предоставляет данные для панели аналитики и графиков.

7. **scheduler-service**
   - Запускает периодические задачи.
   - Выполняет синхронизацию символов.
   - Запускает обновление свечей и перерасчёт аналитики.

8. **nginx**
   - Принимает публичный HTTPS-трафик.
   - Передаёт запросы в api-gateway.
   - Закрывает внутренние сервисы от прямого доступа извне.

#### 3.3.2. Клиентская часть

Клиентская часть реализована на React и TypeScript. Она включает следующие разделы:

- страница входа;
- страница регистрации;
- страница подтверждения почты;
- главная панель с рыночными показателями;
- список торговых пар;
- карточка отдельной торговой пары;
- временная шкала риска;
- страница аналитики;
- настройки аккаунта;
- управление API-ключами.

#### 3.3.3. База данных

В PostgreSQL хранятся следующие основные группы данных:

```text
liquidyne/
├── users                         пользователи
├── refresh_tokens                refresh-токены
├── api_keys                      пользовательские API-ключи
├── exchanges                     биржи
├── symbols                       торговые пары
├── watchlists                    списки наблюдения
├── trades                        сделки
├── liquidations                  ликвидации
├── open_interest_snapshots       снимки открытого интереса
├── candles                       свечные данные
├── analytics_liquidation_spikes  всплески ликвидаций
├── analytics_oi_delta            изменение открытого интереса
├── analytics_volume_imbalance    соотношение объёма и ликвидаций
├── analytics_risk_scores         показатели риска
├── ingestion_offsets             состояние обработки данных
└── jobs                          служебные задачи
```

## 5. Вызов и загрузка

### 5.1. Способ вызова программы

Пользовательская часть вызывается через веб-браузер по адресу развёрнутого фронтенда.

Серверный API вызывается по HTTPS через домен вида:

```text
https://api.[домен]/
```

При локальном запуске адреса и порты задаются настройками Docker Compose.

### 5.2. Входные точки пользовательского интерфейса

Основные маршруты клиентской части:

- `/login` — вход пользователя;
- `/register` — регистрация пользователя;
- `/verify-email` — подтверждение почты;
- `/dashboard` — главная аналитическая панель;
- `/symbols` — список торговых пар;
- `/symbols/:symbol` — страница выбранной торговой пары;
- `/risk` — временная шкала риска;
- `/analytics` — аналитические показатели;
- `/settings/account` — настройки аккаунта;
- `/settings/api-keys` — управление API-ключами.

### 5.3. Основные входные точки API

Основные маршруты внешнего API:

- `POST /auth/register` — регистрация;
- `POST /auth/login` — вход;
- `POST /auth/verify-email` — подтверждение почты;
- `POST /auth/resend-verification` — повторная отправка письма;
- `POST /auth/refresh` — обновление токена;
- `POST /api-keys` — создание API-ключа;
- `GET /symbols` — список торговых пар;
- `GET /market/trades` — сделки;
- `GET /market/liquidations` — ликвидации;
- `GET /market/open-interest` — открытый интерес;
- `GET /market/candles` — свечные данные;
- `GET /analytics/liquidation-spikes` — всплески ликвидаций;
- `GET /analytics/open-interest-delta` — изменение открытого интереса;
- `GET /analytics/volume-liquidation-imbalance` — соотношение объёма и ликвидаций;
- `GET /analytics/risk-score` — показатель риска;
- `GET /visuals/risk-timeline` — данные временной шкалы риска;
- `GET /visuals/risk-timeline/stream` — поток обновлений временной шкалы риска;
- `GET /health` — проверка состояния сервиса.

### 5.4. Требования к памяти

Ориентировочные требования:

- api-gateway: от 128 МБ;
- отдельные Go-сервисы: от 128 МБ на сервис;
- PostgreSQL: от 512 МБ для небольшой базы;
- Kafka: от 1 ГБ;
- nginx: от 64 МБ;
- клиентский браузер: от 512 МБ.

Фактическое потребление зависит от количества торговых пар, глубины истории, частоты поступления событий и числа пользователей.

## 6. Входные данные

### 6.1. Характер и организация входных данных

Входными данными являются:

- рыночные события с криптовалютных бирж;
- список бирж и торговых пар;
- свечные данные;
- данные об открытом интересе;
- данные о ликвидациях;
- данные о сделках;
- параметры запросов пользователя: биржа, торговая пара, период, интервал;
- регистрационные и авторизационные данные пользователя;
- настройки списка наблюдения;
- API-ключи пользователя.

### 6.2. Формат и способ кодирования

Используются следующие форматы:

- JSON для внешнего REST API;
- Protocol Buffers для gRPC;
- HTTPS для обмена с внешними биржами и клиентами;
- PostgreSQL-типы для хранения структурированных данных;
- временные метки в формате, пригодном для передачи через API и хранения в базе данных;
- UTF-8 для текстовых данных.

### 7.1. Характер и организация выходных данных

- ответы внешнего API в формате JSON;
- поток обновлений временной шкалы риска;
- журналы работы сервисов;
- резервные копии базы данных.

### 7.2. Формат и способ представления

Выходные данные представляются в следующих форматах:

- HTML/CSS/JavaScript в веб-интерфейсе;
- JSON для REST API;
- Server-Sent Events для потокового обновления временной шкалы риска;
- OpenAPI-документация для описания API;
- SQL-дампы в сжатом виде для резервного копирования PostgreSQL;
- Docker-образы для развёртывания серверных сервисов.

## 8. Требования к безопасности

Система должна обеспечивать:

- передачу данных через HTTPS в продуктивной среде;
- хранение паролей только в виде хешей;
- хранение API-ключей только в защищённом виде;
- использование JWT для доступа к защищённым маршрутам;
- использование refresh-токенов для обновления сессии;
- ограничение частоты запросов;
- ограничение размера тела запроса;
- настройку CORS для разрешённых доменов;
- отсутствие публичного доступа к PostgreSQL, Kafka и внутренним gRPC-сервисам.

## 9. Требования к сопровождению

Для сопровождения проекта должны быть предусмотрены:

- Docker Compose-файлы для разных режимов запуска;
- документация по развёртыванию;
- пример production-настроек без секретов;
- скрипт развёртывания;
- скрипт резервного копирования PostgreSQL;
- автоматическая сборка Docker-образов;
- автоматический запуск проверок при изменениях в репозитории;
- возможность отката на предыдущий образ сервиса.

## 10. Перспективы развития

В дальнейшем проект может быть расширен следующими возможностями:

- подключение новых криптовалютных бирж через слой адаптеров;
- расширение набора аналитических показателей;
- уведомления о превышении заданного уровня риска;
- пользовательские пороги риска;
- дополнительные графики и наложения на временную шкалу;
- оптимизация хранения больших объёмов исторических данных;
- более гибкая система ролей и прав доступа;
- экспорт аналитических отчётов.
